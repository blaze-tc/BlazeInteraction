# Blaze Interaction 控制台 UI、Camera 预览与稳定性设计

日期：2026-08-27  
状态：已确认  
范围：设备选择界面、CameraVision 控制界面、Radar 控制界面以及相关显示管线

## 1. 背景与目标

当前 CameraVision 控制界面与设备选择界面尚未统一到 Radar 控制台的视觉体系；Camera 每帧复制完整图像并重建大量 WPF 图元，操作参数时会明显卡顿。Radar 的 UI 更新可能在 Dispatcher 中积压，多个点云视图又会重复渲染历史点，在高点数、连续缩放、放大编辑或连续调参时存在卡死和崩溃风险。

本批次目标：

1. 让设备选择、CameraVision、Radar 三个界面使用统一的 Radar 深色视觉语言。
2. 为 CameraVision 提供同时可见的原始画面、四角区域画面和 Unity 点位画面。
3. 将 Camera 设备、分辨率与帧率改为设备能力驱动的联动下拉选择。
4. 解耦 Camera 采集、识别、Unity 输出与 UI 预览，消除参数操作卡顿。
5. 消除 Radar UI 消息积压与重复重绘，保证高点数、缩放、放大编辑和参数输入稳定。
6. 保持 Unity 现有 `InteractionPoint` API 与使用方式兼容。

## 2. 非目标

- 不改变 Camera 手部识别模型和骨骼定义。
- 不限制业务层可识别的手数量；实际数量只受模型、配置和硬件能力影响。
- 不改变 Radar 的处理、区域判断或 IPC 数据语义。
- 不以降低 Camera 识别频率或 Unity 输出频率来换取 UI 流畅度。
- 不在本批次将 WPF 渲染整体迁移到 Direct3D、Skia 或其他新图形框架。

## 3. 统一视觉体系

建立可被 Bridge 主程序、Radar 控制台和 CameraVision Provider 共同加载的 WPF 主题资源。视觉基准沿用 Radar 控制台：

- 应用背景：深海军蓝。
- 内容卡片：深色分层面板。
- 主色：青色，用于连接、选中、焦点和主操作。
- 强调色：橙色，用于提示和重点数据。
- 危险色：红色，用于无效输入和设备异常。
- 统一 Window、Button、ComboBox、TextBox、CheckBox、TabControl、ListBox、卡片、标题、状态标记和验证样式。

设备选择界面改为深色卡片式选择器，使用统一的悬停、选中、禁用和主按钮状态。CameraVision 控制界面采用与 Radar 相同的顶部状态栏、卡片边框、间距和参数控件。共享主题必须只有一个维护来源，避免把 RadarTheme 分别复制到多个程序集后产生漂移。

## 4. CameraVision 界面结构

### 4.1 总体布局

窗口由顶部状态栏、左侧三层预览区和右侧参数区组成。

左侧三层预览始终同时可见，建议初始高度比例为 60% / 20% / 20%，并为每层设置最小可用高度：

1. **左上主画面：原始摄像机画面**
   - 保持摄像机实际分辨率的宽高比。
   - 使用等比缩放，空余区域留黑。
   - 不拉伸、不裁切。
   - 在画面上显示四角控制点和边界线，支持拖动调整。
2. **左中诊断画面：四角有效区域**
   - 显示四角选择结果。
   - 显示经过透视矫正后的矩形有效区域。
   - 与同一处理时间戳的原始画面同步。
3. **左下诊断画面：Unity 输出预览**
   - 按 Unity 输出分辨率等比显示。
   - 每只手显示一个中心点和 21 个独立骨骼关节点。
   - 不绘制骨骼连接线。
   - 画面内容必须来自实际准备发送给 Unity 的数据，而不是独立重新计算。

右侧参数区分为“设备、识别、区域、输出、状态”五个分组。窗口缩放时右侧参数区保持可操作宽度，左侧预览按可用空间等比调整。

### 4.2 顶部状态

顶部持续展示：

- Unity：未连接、连接中、已连接、断开。
- 摄像机：未打开、打开中、已连接、异常。
- 实际采集分辨率。
- 实际采集 FPS。
- 当前识别手数量。

异常状态显示简短原因，完整信息写入诊断日志。

## 5. Camera 设备能力与配置

设备配置按“摄像机 → 分辨率 → 帧率”联动：

1. 选择摄像机后读取该设备支持的分辨率与帧率组合。
2. 分辨率下拉框只显示当前设备可用的分辨率。
3. 帧率下拉框只显示当前设备在所选分辨率下支持的帧率。
4. 无法完整枚举能力的设备使用常用兼容预设作为回退。
5. 打开设备后展示实际生效的分辨率和 FPS。
6. 如果设备拒绝配置，回退到距离目标最近的可用组合，并在界面中明确提示。

Camera 与 Radar 配置继续保存在当前 Unity 项目或打包项目各自的独立沙盒内。两种模式分别保存，互不覆盖。切换摄像机时读取该设备最后一次有效配置；首次使用时创建默认配置。

## 6. Unity 数据兼容

Unity 现有 `InteractionPoint` 公共结构、事件和使用方式保持不变。允许在包内部增加非破坏性的封装或辅助访问方法，但不能要求现有项目修改接收代码。

Camera 模式中，每只识别到的手对应一个 `InteractionPoint`：

- `InteractionPoint.PixelPosition`：该只手计算得到的中心点。
- `InteractionPoint.Fp`：该只手的 21 个实际骨骼关节点坐标。

Radar 模式保持原有语义：

- `InteractionPoint.PixelPosition`：雷达目标中心点。
- `InteractionPoint.Fp`：该目标的实际扫描点。

两种 Provider 继续通过相同结构完成序列化、IPC 和 Unity 事件分发。

## 7. Camera 显示管线优化

Camera 采集、手部识别、Unity 输出和 WPF 预览分离：

- 采集、识别和 Unity 输出继续按配置频率运行。
- UI 只消费最新可用快照；旧的待显示快照被覆盖，不排队补画。
- UI 预览默认上限为 15 FPS，并允许配置。
- 使用可复用图像缓冲区更新画面，避免每帧创建完整图像副本。
- 三个预览使用自绘层或等价的可复用绘制结构，不为每个点反复创建 WPF 控件。
- 原始画面、四角矫正画面和 Unity 点位画面共享同一份带时间戳处理结果。
- 调参、拖动四角或缩放窗口时，控制输入优先于非关键预览重绘。

坐标转换必须基于实际等比显示矩形。黑边区域不参与四角拖动映射；图像、四角控制点、透视区域和 Unity 点位在任何窗口尺寸下都使用同一套可测试转换。

## 8. Radar 显示管线优化

- 每台 Radar 在 UI Dispatcher 前只保留最新待显示快照，避免更新队列无界增长。
- 一次数据快照引起的多个属性变化合并为一次显示刷新。
- 原始点、过滤点、融合画面和放大编辑窗口共享整理后的显示帧，避免重复转换。
- 高点数下根据显示面积进行纯视觉抽样，并自动减少历史轨迹层数。
- 连续缩放期间使用轻量显示；缩放停止后恢复当前视口可见细节。
- 参数输入时只校验当前字段；输入稳定或“保存并应用”时执行完整配置校验。
- 关闭窗口、切换设备或 Provider 停止期间到达的更新必须安全丢弃。

显示抽样和轨迹层数调整只影响控制台画面。Radar 的原始点、过滤处理、区域判断、IPC 和 Unity 输出必须保持完整。

## 9. 错误处理与诊断

设备能力枚举失败、设备打开失败、配置回退、预览丢帧和绘制异常均应产生结构化诊断信息。日志至少包含：

- Provider 和设备标识。
- 实际分辨率和 FPS。
- Camera 识别手数量。
- Radar 输入点数、显示点数和轨迹层数。
- UI 接收快照数、实际绘制数和被覆盖的旧快照数。
- 异常类型、消息和堆栈。

对非法数值、极端点数、窗口关闭竞态和 Provider 生命周期切换增加边界保护；可恢复的显示错误不得导致 Bridge 进程退出。

## 10. 测试策略

每个实施批次严格执行：先写失败测试，再实现，再运行该批次相关完整测试。

### 10.1 共享主题

- 验证选择模式、CameraVision 和 Radar 加载同一主题资源。
- 验证关键控件的默认、悬停、选中、禁用、焦点和错误状态。
- 验证窗口缩放时布局不重叠、不丢失关键操作。

### 10.2 Camera 三画面与设备能力

- 验证三画面同时存在并按上、中、下排列。
- 验证常见与极端分辨率下的等比缩放、黑边和坐标映射。
- 验证四角区域和透视矫正结果。
- 验证 Unity 预览只显示中心点和 21 个骨骼点，不显示连接线。
- 验证设备、分辨率和帧率联动以及不支持组合的回退。

### 10.3 Camera 性能

- 使用持续视频帧和多手模拟数据验证 UI 只消费最新快照。
- 验证 UI 预览限帧不降低识别或 Unity 输出频率。
- 验证持续调参、拖动四角和缩放时没有 UI 队列积压或持续内存增长。

### 10.4 Radar 回归与稳定性

- 所有 Radar 现有测试必须先通过，任何 Radar 回归优先修复。
- 覆盖高点数、多历史帧、连续缩放、放大编辑窗口反复开关和连续参数输入。
- 验证显示抽样不改变处理点、区域结果、IPC 与 Unity 输出。
- 运行 Radar、Interaction Core、Provider、IPC 和 Unity Package 的相关完整测试。

### 10.5 协议兼容

- Camera：一个手对应一个 `InteractionPoint`，中心点进入 `PixelPosition`，21 个骨骼点进入 `Fp`。
- Radar：中心点和实际扫描点语义保持不变。
- 验证两种数据的序列化、IPC 和 Unity 事件没有破坏性变化。

## 11. 实机验收标准

Camera：

- 可切换实际摄像机、分辨率和帧率。
- 三个画面同步且保持正确比例。
- 多手中心点和 21 个骨骼点可稳定进入 Unity。
- 连续调整参数和四角区域时界面保持响应。

Radar：

- 模拟高点数和实际 Radar 均可持续运行。
- 连续缩放、打开/关闭放大编辑和连续调参不崩溃、不长期卡死。
- 高点数下 Unity 仍接收完整数据。

共同标准：

- 没有未处理异常。
- UI 队列和内存不存在持续无界增长。
- CPU、内存、实际 FPS 和快照覆盖计数有可复核记录。
- 所有相关自动化测试通过后，才能判定本批次完成。
